## Problem

**This package writes a field it cannot read back.**

`ManifestBuilder` accepts a `SoftwareAgent` and writes `softwareAgent` into the
`c2pa.created` action (`ManifestBuilder.php`, `'softwareAgent' => $agent->toArray()`).
`SignAssetJob` takes a name and an optional version for the same purpose. The
Article 50 marking this package exists for is *defined* as that action carrying a
`digitalSourceType` **and** a `softwareAgent { name }` — both halves, per the
domain rules in CLAUDE.md.

On the reading side, `ManifestReport` exposes `digitalSourceTypes()` and nothing
for the agent. The data arrives intact — `BuildReadRoundTripPropertyTest` asserts
on `$action['softwareAgent']['name']` — but it is reachable only by walking
`assertions()` and reproducing the package's own knowledge of where the field
sits: which labels count as actions assertions, that `data.actions` is a list,
that entries may be malformed. Every consumer that wants "which system made
this" writes that walk again, and gets the label rule wrong the first time.

That asymmetry is the whole problem. `digitalSourceTypes()` already encapsulates
exactly this traversal for the other half of the same assertion. The second
question a caller asks after "is this AI-generated" is "generated by what", and
today the answer is available only to a caller willing to re-implement the
package's internals.

## Scope

**In scope**

- A read-side accessor on `ManifestReport` returning the software agents named by
  the active manifest's actions assertions.
- The same assertion-label rule `digitalSourceTypes()` uses: any label starting
  `c2pa.actions`, so both `c2pa.actions` and `c2pa.actions.v2` are covered.
- De-duplication and stable ordering, mirroring `digitalSourceTypes()`.
- Tolerating every malformed shape a third-party manifest can present, without
  throwing and without inventing values.

**Out of scope** (each needs its own spec before it may be built)

- **`claim_generator_info` / the claim generator.** A different field in a
  different place, describing the tool that produced the *claim* rather than the
  agent named by an *action*. Related enough to be confused with this; distinct
  enough to need its own criteria.
- **A singular accessor** (`softwareAgent(): ?SoftwareAgent`) with a precedence
  rule for picking one when several are present. Deciding which agent is "the"
  agent is a policy question, and this spec deliberately reports what is there.
- **Raw manifest access.** Returning the undecoded manifest so a caller can walk
  it freely is a separate concern and would weaken the case for accessors.
- Any change to `ManifestBuilder`, `SoftwareAgent` or the signing path. This is
  read-side only.
- Surfacing the agent in the Laravel `read` command output or in `ManifestReport`
  serialisation.

## Behavior

Acceptance criteria as Given/When/Then. Each is individually testable and will be
covered by a Pest test tagged `->group('SPEC-033')`.

- **AC1 — the agent this package writes is the agent it reads**
  - Given a manifest built by `ManifestBuilder::forAiGenerated()` with
    `withSoftwareAgent($name, $version)`
  - When the signed asset is read back and the accessor is called
  - Then it returns exactly one agent, with that name and that version

- **AC2 — an absent version is absent, not empty**
  - Given an action whose `softwareAgent` carries a `name` and no `version`
  - When the accessor is called
  - Then the entry's version is `null`, and is not coerced to `''`

- **AC3 — several actions, distinct agents, first-appearance order**
  - Given an actions assertion naming two different agents, and a third entry
    repeating the first
  - When the accessor is called
  - Then two agents are returned, in the order first encountered, with no
    duplicate — matching `digitalSourceTypes()` behaviour on the same input

- **AC4 — the name is returned verbatim** *(adversarial input)*
  - Given an agent name containing JSON, markup, newlines or control characters,
    as `Gen::softwareAgentName()` already generates
  - When the accessor is called
  - Then the name is returned byte-for-byte, with no unescaping, interpretation
    or truncation, and the `digitalSourceType` of the same action is unaffected

- **AC5 — a malformed `softwareAgent` is skipped, not guessed** *(required:
  error / malformed input)*
  - Given actions whose `softwareAgent` is a string, an integer, a list, an
    object without a `name`, or an object whose `name` is not a string
  - When the accessor is called
  - Then each such action contributes nothing, no exception is thrown, no
    partial entry is produced, and well-formed entries in the same assertion are
    still returned

- **AC6 — nothing to report is an empty list**
  - Given a report with no manifest, or a manifest with no actions assertion, or
    an actions assertion whose `data.actions` is absent or not a list
  - When the accessor is called
  - Then an empty list is returned and `hasManifest()` is unaffected

- **AC7 — both actions labels are honoured**
  - Given an actions assertion labelled `c2pa.actions` and one labelled
    `c2pa.actions.v2` in the same manifest
  - When the accessor is called
  - Then agents from both are returned, per the label rule
    `digitalSourceTypes()` already applies

## API sketch

Illustrative only. `strict_types=1`, accessor on the existing `final`
`ManifestReport`, no new state on the constructor — the value is derived from
`assertions()` exactly as `digitalSourceTypes()` is.

```php
// namespace Provemark\ContentCredentials\Core\Reading;

/**
 * Distinct software agents named across the active manifest's actions
 * assertions (any label starting `c2pa.actions`, per D5).
 *
 * @return list<SoftwareAgent>
 */
public function softwareAgents(): array;
```

Mirrored against the existing accessor so the pair reads as one idea:

```php
$report->digitalSourceTypes();   // list<string>  — what kind of source
$report->softwareAgents();       // list<SoftwareAgent> — produced by what
```

## Open questions

- **What the list contains — RESOLVED at approval, 2026-08-12: reuse
  `Core\Manifest\SoftwareAgent`.** It is the package's existing vocabulary for
  the concept, it makes read-then-rebuild trivial, and deptrac permits it —
  `Core` is a single layer, so `Reading` → `Manifest` is intra-layer and
  unconstrained. The argument against is recorded rather than discarded: that
  class is a write-side object carrying `toArray()`, which a read result has no
  use for. If that proves wrong, the alternatives were a read-side value object
  or `list<array{name: string, version: ?string}>`, and the change would be
  breaking once published.

  **Amended at implementation, 2026-08-12.** The draft argued this would be the
  *first* deliberate coupling between the two halves of Core. That was wrong:
  `ManifestReport` already imported `Core\Manifest\DigitalSourceType`, and
  `isAiGenerated()` has always run on it. The coupling long predates this spec,
  so `SoftwareAgent` follows an established pattern rather than setting a
  precedent. The correction strengthens the decision instead of weakening it,
  which is why it is recorded here rather than reopening the question.
- **Naming — non-blocker.** `softwareAgents()` mirrors the C2PA field name and
  `digitalSourceTypes()`'s plural. `generators()` would read better in English
  and worse against the spec.
- **Does anything else deserve the same treatment — non-blocker.** The action
  verb itself (`c2pa.created` vs `c2pa.opened`) is reachable only by the same
  walk. Not in this spec; worth noticing that the asymmetry may be wider than
  one field.

Notes for a later reader:

- **AC4 lives in the property suite, not beside the others.** It is quantified
  over `Gen::softwareAgentName()`, and the Eris DSL is only permitted under
  `tests/**/Property/`, which `phpstan.neon` excludes from level-max analysis for
  the reasons stated there. Writing it in `tests/Unit/Reading/` produced six
  PHPStan errors; moving it was the fix, not an ignore.
- **`actions()` is a new private helper** extracting the shared traversal.
  `digitalSourceTypes()` still carries its own copy of that walk — see the
  follow-up note below.
- **Every test was seen to fail first**, with
  `Call to undefined method ...::softwareAgents()`, before any implementation
  existed.

## Follow-up, decided at implementation (2026-08-12)

The first cut of this implementation left `digitalSourceTypes()` carrying its own
copy of the traversal `actions()` now encapsulates — the same label rule, the
same list check, the same skip of non-array entries. Two copies of one rule is
exactly the drift this spec's Problem section complains about, and this work
introduced the second copy.

**Collapsed on the maintainer's decision rather than silently**, because the
refactor touches a method governed by earlier specs. It changes no behaviour:
`digitalSourceTypes()` now walks `actions()` and applies its own filter, the
suite is unchanged at 348 passing, and `isAiGenerated()` and
`involvesGenerativeAi()` were already delegating to `digitalSourceTypes()`, so
one traversal now serves all four accessors.
